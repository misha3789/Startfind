# ADR-001: единый контракт данных MVP

- Статус: принят
- Дата: 24.11.2026
- Источник истины: `архитектура 2.pdf`, раздел организации данных
- Машиночитаемая версия: [`data-contract.json`](data-contract.json)

## Решение

MVP использует 11 таблиц, перечисленных в `data-contract.json`. Миграции,
SQLAlchemy-модели и тесты схемы должны строиться по этому контракту. Имена
колонок из контракта являются каноническими; API DTO могут иметь собственные
имена только с явным преобразованием на границе Presentation Layer.

В архитектурной таблице `projects` не было колонки `status`, хотя отдельное
ограничение задаёт её значения. Контракт добавляет `projects.status` рядом с
`projects.recruitment_status`, поскольку это два разных состояния:

- `status`: жизненный цикл проекта — `draft`, `active`, `completed`, `archived`;
- `recruitment_status`: состояние набора — `draft`, `open`, `closed`.

## Разрешённые расхождения

### Статусы отклика

Канонический набор: `sent`, `viewed`, `accepted`, `rejected`, `postponed`.
Значение `withdrawn`, присутствовавшее в тестовой заготовке и подробном плане,
не входит в архитектурный PDF и исключено из MVP. Его добавление потребует
отдельного ADR и миграции.

### Участник команды

`team_members` связывает проект, роль проекта и профиль специалиста:
`project_id`, `project_role_id`, `specialist_profile_id`. Прямая ссылка
`user_id` из тестовой заготовки удалена из контракта как дублирующая путь
`specialist_profile_id -> specialist_profiles.user_id`.

### Профиль специалиста

Входной контракт MVP содержит `direction`, `skills`, `hours_per_week` и
`portfolio`. Каждый элемент `skills` содержит `skill_id` и `level`; допустимые
уровни: `basic`, `confident`, `advanced`. Поле `topics`, встречавшееся в плане,
не представлено в архитектурной модели и не входит в MVP-контракт.

### PostgreSQL и pgvector

Основное хранилище — PostgreSQL. Подбор в MVP детерминированный. pgvector может
быть установлен как расширение для будущего `EmbeddingService`, но в текущем
контракте нет векторных колонок, и работоспособность MVP от расширения не
зависит.

## Последствия

- модели и миграции должны использовать `projects.owner_id`, а не
  `founder_id`;
- `team_members` ссылается на `specialist_profiles`, `project_roles` и
  `projects`;
- тесты не должны принимать `applications.status = 'withdrawn'`;
- изменение перечисленных решений выполняется через новый ADR с обновлением
  `data-contract.json` и контрактных тестов.
